## 0. 세션 역할

현재 대화 세션은 프로토타입 개발 전략과 실행 계획을 확정하는 범위다. 구현 브랜치 생성과 실제 Godot 개발은 이 세션에서 하지 않으며, 사용자가 별도로 시작하는 새 개발 세션에서 승인된 영어 정본 계획을 기준으로 진행한다.

## 1. 확정된 방향

프로토타입은 Windows PC, 16:9, 마우스 조작으로 고정한다. 모바일·터치·게임패드 대응은 프로토타입 검증 이후 본 개발에서 다룬다.

세션은 Mini Metro를 참고한 탑다운 정사영 2D 화면으로 구성한다. 중앙 지도를 가장 넓게 유지하고, 얇은 상단 HUD에는 시간·선로·현금·내구도를, 하단 HUD에는 계약 진행·화물칸·선로 끝 경고를 배치한다.

최종 프로토타입은 한 번의 운행 데모가 아니다. 계약 선택, 워프 운행, 정산, 대출을 통한 적자 복구, 다음 주기 반복, 파산까지 전체 루프가 작동해야 한다.

## 2. 브랜치 분리

- Development: 향후 본 개발 통합 브랜치
- Prototyping: 프로토타입 전용 통합 브랜치
- proto/*: Prototyping에서 분기하는 짧은 피처 브랜치

Prototyping은 현재 main 기준점에서 생성하고 Development에서 분기하지 않는다. 현재 두 브랜치가 같은 커밋을 가리키더라도 역할과 병합 경계를 명확히 유지한다.

프로토타입이 끝나도 Prototyping 전체를 Development에 병합하지 않는다. 검증된 규칙, 수치 범위, UX 결론, 아트 요구사항을 영어 본 개발 명세로 옮긴 뒤 재사용 가치가 검증된 데이터·순수 로직·테스트만 선별 이식한다.

## 3. 개발 방식

프로토타입은 순차형 버티컬 슬라이스로 개발한다. 각 피처 브랜치는 직전 피처가 Prototyping에 병합된 뒤 최신 Prototyping에서 분기한다.

매 병합 시점의 Prototyping은 다음 조건을 만족해야 한다.

- 정상 실행 가능
- 직전까지 구현된 기능을 실제로 플레이 가능
- 자동 테스트 통과
- Windows 16:9 수동 스모크 테스트 통과

UI는 별도 장기 브랜치로 분리하지 않는다. 각 기능 브랜치가 해당 기능을 읽고 조작하는 데 필요한 UI까지 함께 구현해 Godot 씬 충돌을 줄인다.

## 4. 피처 브랜치

### proto/00-foundation

현재 Git에 포함되지 않은 Godot 프로젝트를 등록하고 폴더 구조, 입력, Windows·16:9 설정, 헤드리스 테스트 러너, 밸런스 데이터와 RNG 시드 입력을 마련한다.

### proto/01-session-shell

탑다운 2D 필드, 상·하단 HUD, 조절 가능한 UI 패딩, 세션 타이머, 정기 종료와 결과 전환을 만든다.

### proto/02-track-train

에디터에 배치한 출차 후보, 출차 전 예약·순차 건설, 좌클릭 끝점 드래그, 우클릭 무료 예약 취소, 선로 재고, 후방 자동 회수, 고정 속도 기차, 완성 선로 끝 조기 종료를 구현한다. 논리 필드와 기능별 밸런스 수치는 Inspector에서 조정한다.

### proto/03-warp-cargo

시드 기반 워프 쌍의 예고·활성·만료, 자동 적재·배송, 화물칸 제한, 즉시 운송료를 구현한다.

### proto/04-risk-investment

위험 지형, 거리 기반 피해, 내구도, 완성 선로 유료 철거, 같은 비용의 입체교차, 세션 한정 선로·화물칸 구매를 구현한다. 미주행 선로는 클릭 지점 이후를, 주행 완료 후방 선로는 활성 후방 시작점부터 클릭 지점까지 철거한다.

### proto/05-contract-economy

6개 업체, 단일 계약 선택, 할당량, 운송료, 보너스·위약금, 초과 신뢰도, 수리비·운영비 정산을 구현해 한 주기를 완성한다.

### proto/06-credit-survival

업체별 신용한도, 고정금리, 대출과 자동 상환, 돌려막기, 적자 복구, 난이도 상승, 파산을 구현해 전체 반복 루프를 완성한다.

### proto/07-playtest-ready

시드·이벤트 기록, 재현 기능, 플레이테스트 지표, 파산 결과, 밸런스 데이터 정리, Windows 실행 빌드를 완성한다.

## 5. 기능과 표현의 경계

게임 규칙은 테스트 가능한 GDScript 모델과 계산기에 둔다. Node2D, Line2D, Control, Container, CanvasLayer는 입력과 화면 표현만 담당한다.

현금은 EconomySystem만, 계약 실적은 ContractSystem만 변경한다. 화면 노드는 현금·신뢰도·채무·배송 수를 직접 수정할 수 없다.

여기서 TrackSystem·EconomySystem 같은 구분은 책임과 상태 소유권의 경계다. 프로토타입의 모든 피처에 인터페이스나 추상 기반 클래스를 만들라는 뜻이 아니다. 본 개발 재사용을 예상한 추상화 계층은 프로토타입에 미리 추가하지 않고, 테스트와 소유권 규칙을 지키는 범위에서 구체 구현으로 진행한다.

SessionController가 고정 물리 틱에서 다음 순서를 관리한다.

1. 우클릭 예약 취소 또는 승인된 유료 철거
2. 좌클릭 드래그 선로 예약
3. 실제 선로 건설과 출차 준비 완료 판정
4. 기차 이동과 완성 선로 끝 판정
5. 출발지·목적지 통과
6. 위험 지형 피해
7. 후방 자동 회수
8. 워프 만료
9. 세션 시간 만료
10. 종료 사유 확정
11. 한 번의 정산
12. 화면 상태와 완료 결과 갱신

물리 신호 호출 순서에 게임 결과를 맡기지 않는다. 기차의 이전 위치와 현재 위치 사이를 직접 검사한다.

## 6. 조절 가능한 UI 패딩

기능과 아트는 분리하지만, UI 배치 수치는 의도적으로 조절 가능하게 둔다.

UILayoutProfile 리소스에서 다음 값을 관리한다.

- 가로·세로 외부 패딩
- 패널 내부 패딩
- 항목 간격과 행 간격
- HUD 높이
- 아이콘 크기

Godot Control과 Container가 값 변경에 따라 자동으로 재배치된다. 프로토타입에서는 Inspector에서 개발자가 조정하며, 사용자용 설정 화면은 만들지 않는다. 최솟값과 최댓값을 검증해 과도한 패딩이 지도 영역을 침범하지 못하게 한다.

본 개발에서는 같은 구조를 사용자용 UI 배율 설정으로 확장할 수 있다.

## 7. 테스트와 병합

모든 브랜치는 다음 세 단계 검증을 통과해야 한다.

1. 순수 로직 단위 테스트
2. 고정 시드 통합 시나리오
3. Windows 16:9 수동 플레이

외부 테스트 플러그인 의존성을 추가하지 않고 Godot 네이티브 GDScript 헤드리스 러너를 사용한다.

테스트를 끄거나 건너뛴 상태로 병합하지 않는다. 생성 캐시, 로컬 로그, 플레이테스트 개인정보도 Git에 포함하지 않는다.

각 피처를 Prototyping에 스쿼시 병합한 뒤 prototype-m1부터 prototype-m8까지 순서대로 태그를 남긴다.

## 8. 아트 리소스와 다음 단계

현재 프로토타입은 도형, 색상, 기본 폰트, 교체 가능한 임시 효과음만 사용한다.

최종 텍스처·아이콘·폰트·애니메이션·오디오는 View와 Theme 경계에서 교체할 수 있어야 한다. 아트를 바꾸기 위해 선로, 화물, 계약, 경제, 대출 계산 코드를 수정해야 한다면 구조 위반이다.

커스텀 아트 제작 범위는 피처 구조가 안정된 뒤 실제로 필요한 상태·경고·화면 목록을 기준으로 별도 산정한다.

## 9. 프로토타입 종료 판단

기능이 모두 동작하는 것만으로 검증 성공으로 보지 않는다. 반복 플레이에서 다음 세 판단이 실제로 관찰되어야 한다.

- 회수되는 선로를 계산하며 기차 앞 선로를 유지하는 판단
- 제한된 화물칸 안에서 계약 화물을 우선하는 판단
- 현재 세션에 투자할 현금과 다음 주기에 남길 현금을 비교하는 판단

관찰 결과와 실패한 가정까지 기록해 본 개발의 입력으로 사용한다.

본 개발을 시작하기 전에는 프로토타입에서 확인된 변경 지점, 대체 구현 필요성, 테스트 경계와 재사용 후보를 근거로 추상화 범위를 별도로 검토한다. 인터페이스·합성 경계·다형성·구체 구현 중 무엇을 사용할지는 그때 결정하고 본 개발 코드에서 적용한다. 이를 위해 가능성은 열어두되, Prototyping을 본 개발 구조처럼 만들기 위한 선행 추상화나 사후 리팩터링은 하지 않는다.
