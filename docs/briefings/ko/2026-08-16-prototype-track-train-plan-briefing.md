## Task 2 에디터 게이트 개정

기존 custom `SceneTree` 스크립트 러너와 그 `.gd.uid`는 추적하지 않고 제거합니다. 대신 아래 세 파일과 `project.godot`의 정확한 플러그인 활성화 설정을 Task 2 범위에 추가합니다.

- `addons/moerail_test_editor_gate/plugin.cfg`
- `addons/moerail_test_editor_gate/logical_track_field_editor_gate.gd`
- `addons/moerail_test_editor_gate/logical_track_field_editor_gate.gd.uid`

플러그인은 `--` 뒤에 `--moerail-logical-field-editor-gate`가 전달된 경우에만 실행합니다. 에디터 파일시스템의 `is_scanning()` 상태가 끝날 때까지 프로세스 프레임 단위로 기다리고, 실제 논리 필드 씬의 프리셋·`CUSTOM` 경계·후보 정규화 위치를 검사합니다. 성공 시 정확한 PASS 마커를 한 번 출력한 뒤 반환합니다. 플러그인은 닫기 알림을 전파하거나 `SceneTree.quit`, 에디터 재시작, 다른 종료 API를 호출하지 않습니다.

실기능 워크트리에서 에디터를 직접 실행한 두 번째 개정은 검증과 종료에는 성공했지만, 에디터가 무시된 프로젝트 상태와 사용자 전역 설정을 읽고 기능 파일을 다시 포맷할 수 있다는 경계를 남겼습니다. 세 번째 개정은 이 실행 경계만 교체합니다. 각 에디터 실행마다 시스템 임시 디렉터리 아래 `moerail-track-train-editor-<guid>` 루트를 새로 만들고, Git이 선택한 추적 파일과 무시되지 않은 미추적 프로젝트 파일만 일반 파일로 복사합니다. `.git`, 기존 `.godot`, ignored 생성물, junction·symlink·reparse point는 복사하지 않으며, 경로 탈출과 복사 전후 파일 목록·SHA-256 불일치를 거부합니다. 미러에서 기능 또는 기본 작업공간으로 어떤 파일도 되돌려 복사하지 않습니다.

플래그 실행과 no-flag 실행은 서로 다른 새 미러를 사용합니다. 복사 전 manifest를 먼저 SHA-256으로 고정하고, 복사 뒤 원본 전체와 미러 전체를 그 manifest에 다시 대조합니다. 원본·목적지·삭제 대상의 모든 조상에서 reparse point를 거부하고 `.git`·`.godot` 구성요소도 명시적으로 거부합니다. 각 자식은 미러 안의 별도 `APPDATA`, `LOCALAPPDATA`, `TEMP`, `TMP`를 받고, 정확히 `--editor --import --quit-after 240 --max-fps 60`과 미러 내부 절대 로그 경로로 실행됩니다. 동적 경로는 문자열 결합이 아니라 `ProcessStartInfo.ArgumentList`에 인수별로 추가하며 stdout·stderr를 비동기로 비웁니다. 정확한 자식 종료 뒤 두 출력 Task에는 별도 5초 완료 제한이 있고, 초과하면 reader를 닫고 실패·미러 보존으로 처리합니다. 240회는 import 준비 이후 명목상 약 4초의 하네스 상한이며 Godot의 시간 보장은 아닙니다. PowerShell은 자신이 시작한 숨김 자식 프로세스만 최대 30초 기다립니다. 자연 종료하지 못하면 먼저 실패로 판정한 뒤 그 정확한 자식만 종료하고 최대 5초만 회수 완료를 기다립니다. 사용자 소유 Godot·Steam 편집기에는 접근하지 않고, 시간 초과나 프로세스 강제 정리는 성공 증거가 아닙니다.

추가로 게이트 인수 없이 활성화된 플러그인을 별도 미러 에디터에서 실행해 PASS/FAIL 마커, 종료 요청, 오류, 누수, 기능 파일 변경이 없음을 확인합니다. stdout·stderr·엔진 로그 세 파일은 모두 실제 일반 파일로 존재해야 하며, 하나라도 없거나 읽을 수 없으면 실패입니다. PASS 마커 개수는 중복될 수 있는 엔진 로그가 아니라 stdout과 stderr에서만 세며, 금지 진단은 stdout·stderr·엔진 로그 전체에서 검사합니다. 두 에디터 실행 모두 `FAIL:`, `SCRIPT ERROR:`, `ERROR:`, `FATAL:`, `WARNING:`, `CRASH:`와 crash handler·signal 종료를 거부하며 `Scan thread aborted`, RID 누수, ObjectDB 누수도 금지합니다. 오류 필터를 완화하거나 출력을 숨기지 않습니다.

이미 생성된 플러그인 UID는 Step 3B에서 에디터 import 없이 형식·유일성·전체 파일 상태 불변만 확인합니다. UID가 없거나 잘못되었으면 기능 에디터를 실행하거나 미러에서 생성해 되돌려 복사하지 않고 중단합니다. 상태 행뿐 아니라 추적 파일과 무시되지 않은 미추적 파일 전체의 SHA-256도 전후 비교하므로, 이미 dirty인 Task 2 파일의 바이트 재작성도 놓치지 않습니다. `prototype_app.gd`는 UID 검증과 두 미러 실행 전후 모두 기능 HEAD와 같아야 합니다.

세 번째 재개 게이트는 어떤 변경보다 먼저 다음을 모두 고정값으로 확인합니다.

- 기본 작업공간의 브랜치·HEAD·빈 인덱스·보호 파일 상태와 SHA-256
- `prototype-m2`, 코드 기준점과 시작 계획의 부모·파일 범위, 원격 `origin/Prototyping`, Godot 정확한 버전

- 현재 예약 끝점에서 좌클릭한 뒤 연속 드래그해야만 선로를 그릴 수 있습니다.
- 드래그 이벤트가 많이 들어와도 고정 물리 틱마다 논리 좌표 하나만 사용합니다.
- 예약은 즉시 총량에서 빠지고, 실제 선로는 별도 건설 속도로 순서대로 만들어집니다.
- 우클릭은 예약·미건설 선로의 선택 지점부터 끝까지 무료 취소하고 길이를 한 번 반환합니다.
- 우클릭은 스트로크를 끝내며, 계속 누른 좌클릭이 자동으로 다시 그리기를 시작하지 않습니다.
- `proto/02`에서 완성 선로 우클릭은 아무 변화가 없습니다. 유료 철거와 입체교차는 `proto/04-risk-investment`에서 같은 주요 선로 작업 비용을 사용하는 별도 기능입니다.
- 선로는 재고, 논리 필드 경계, 활성 선로 교차 중 가장 먼저 만나는 제한점에서 잘립니다.
- 기본 교차 여백은 접촉 전 `4` 논리 단위이며, 지나가서 자동 회수된 좌표는 다시 사용할 수 있습니다.
- 기본 건설 속도는 초당 `120`, 열차 속도는 초당 `60`입니다. 60틱에서 각각 틱당 `2`, `1` 논리 단위입니다.
- 기본 완성 선로가 `360`에 도달하는 정확한 틱에 열차가 처음 이동하고 타이머도 첫 틱을 소비합니다.
- 열차가 현재 완성 선로 끝에 닿으면 예약 선로가 더 있어도 `TRACK_END_REACHED`가 요청됩니다.
- 열차 뒤 기본 `240` 논리 단위보다 먼 선로는 부분 선분을 포함해 연속 회수됩니다.
- 같은 틱에 회수된 재고는 그 틱 스냅샷에 보이지만 다음 틱부터 새 예약에 사용할 수 있습니다.
- 운행 중 경고 시간은 `완성 선로 앞 길이 / 열차 속도`이며 예약·미건설 길이는 포함하지 않습니다.
- 기본 `3.0초` 이하에서 경고가 긴급 표시로 바뀝니다.
- 정규 시간 만료와 선로 끝이 같은 틱에 발생하면 정규 시간 만료가 우선합니다.
- 완료 스냅샷을 먼저 한 번 내보낸 뒤 결과를 한 번 내보내며, 이후 입력과 틱은 모두 무효입니다.

## 구현 이후 승인 게이트

1. 검토된 기능 HEAD와 모든 증거를 사용자에게 보고합니다.
2. 승인 후 별도 `codex/prototype-m3-candidate` 워크트리에서 기능 커밋을 하나로 squash하고 동일 트리인지 검증합니다.
3. 통합 승인을 별도로 받은 뒤에만 `Prototyping`을 fast-forward합니다.
4. 통합 결과 검증과 별도의 태그 승인을 받은 뒤에만 annotated `prototype-m3`를 만듭니다.
5. 태그 승인과 별도의 푸시 승인을 받은 뒤에만 `Prototyping` 브랜치와 태그를 atomic push로 함께 게시합니다.
6. 원격 브랜치 커밋, annotated tag object, peeled commit, GitHub API 결과를 모두 확인합니다.

통합 승인에는 태그가 포함되지 않고, 태그 승인에는 푸시가 포함되지 않습니다. 추가 커밋이나 PR은 만들지 않습니다. 기능·후보 워크트리 정리도 게시 증거 승인 이후 별도 판단으로 남깁니다.

## 계획 승인 후 새 개발 세션에서 선택할 실행 방식

사용자가 이미 선택한 방식은 작업별 새 구현 에이전트와 사양·품질 2단계 검토를 사용하는 `subagent-driven-development`입니다. 직접 구현은 정확한 `nvidia/nvidia-nemotron-3-ultra-550b-a55b`, 웹 조사는 `gpt-5.6-luna`, 사양·품질 검토는 각각 새 `gpt-5.6-sol` 에이전트로 진행합니다. 개정 계획 승인 뒤 같은 방식으로 Task 2를 복구하고 Task 9까지 순서대로 계속합니다. 어느 실행 환경에서도 RED/GREEN, 작업별 파일 범위, 작업별 두 단계 독립 리뷰, 통합·태그·푸시 분리 원칙은 동일합니다.
