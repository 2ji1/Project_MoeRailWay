## 0. 세션 경계

현재 대화에서는 상세 계획 문서만 작성한다. `proto/01-session-shell` 브랜치 생성, Godot 코드 작성, 테스트 구현, 병합과 태그 생성은 별도의 새 개발 세션에서 수행한다.

현재 기본 `Prototyping` 작업공간에는 테스트 파일 2개의 들여쓰기 전용 미커밋 변경이 있다. 새 개발 세션은 이를 수정·스테이징·복사·초기화하지 않고, `prototype-m1` 커밋에서 별도의 워크트리를 만든다.

## 1. 확정된 화면 흐름

이번 마일스톤은 1번 자동 시작 방식으로 확정했다.

1. 메인 씬을 실행한다.
2. 밸런스와 UI 레이아웃 설정을 검증한다.
3. 빈 세션을 즉시 시작한다.
4. 상단 HUD에서 기본 180초 카운트다운을 표시한다.
5. 시간이 0이 되면 같은 메인 씬 안에서 결과 화면으로 한 번만 전환한다.
6. 결과 화면에 머문다.

임시 준비 화면, 시작 버튼, 재시작 버튼, 다음 버튼, 디버그 종료 버튼은 만들지 않는다. 실제 세션 시작 선택은 이후 계약 화면이 구현될 때 담당한다.

## 2. 이번 마일스톤의 범위

- 명시적인 정수 틱 기반 세션 카운트다운
- 정기 시간 만료 결과와 한 번만 실행되는 완료 경계
- Mini Metro를 참고한 탑다운 2D 빈 필드
- 얇은 상단·하단 HUD
- Inspector에서 조절하는 `UILayoutProfile`
- 지원되는 16:9 크기에서 안전한 패딩과 필드 좌표 변환
- 단색·기본 폰트 기반 임시 Theme
- 결과 오버레이
- 자동 테스트용 2초 세션 fixture
- Windows 수동 스모크 체크리스트

선로, 기차, 워프, 화물, 위험 지형, 계약, 현금 변경, 정산, 대출은 구현하지 않는다. 결과 화면에도 가짜 정산 수치를 표시하지 않는다.

## 3. 세션 시간 규칙

세션 도메인은 실제 시간이나 프레임 델타를 읽지 않는다. `SessionStartConfig`의 세션 길이와 틱 수를 받아 다음 규칙으로 정수 틱을 만든다.

- 전체 틱: `ceil(세션 초 × 초당 틱)`
- 시작 전과 종료 후의 추가 틱은 무시
- 마지막 틱에서 남은 시간을 0으로 만든 뒤 정기 종료 결과를 한 번만 발행
- 화면 표시는 남은 틱을 초로 올림해 `M:SS` 형식으로 표시
- 기본 세션은 `3:00`에서 시작해 종료 시점에만 `0:00` 도달

자동 테스트는 틱을 직접 전진시키므로 180초를 기다리지 않는다. 실제 자동 시작과 결과 전환은 별도의 2초 테스트 씬으로 검증하며, 기본 밸런스 값은 바꾸지 않는다.

2초 테스트의 자동 실행은 Godot의 종료 옵션을 실제 초로 오해하지 않도록 60 FPS 고정 시뮬레이션으로 수행한다. 120틱 완료를 180회 반복 이내에서 확인한다.

## 4. UI 레이아웃

화면 중앙의 필드가 가장 넓은 영역을 차지한다.

상단 HUD:

- 실제 동작하는 남은 시간
- 아직 비활성인 선로·현금·내구도 자리

하단 HUD:

- 아직 비활성인 계약·화물칸·선로 끝 경고 자리

미구현 값은 숫자를 꾸며내지 않고 `—`로 표시한다. 나중에 각 기능 브랜치가 자신의 값을 연결할 수 있도록 자리만 안정적으로 유지한다.

`UILayoutProfile`은 다음 값을 독립적으로 조절한다.

- 가로·세로 외부 패딩
- 패널 내부 패딩
- 항목·행 간격
- HUD 높이
- 아이콘 크기

| 항목 | 기본값 | 최솟값 | 최댓값 |
|---|---:|---:|---:|
| 가로 외부 패딩 | 16 | 0 | 48 |
| 세로 외부 패딩 | 12 | 0 | 32 |
| 패널 내부 패딩 | 10 | 4 | 20 |
| 가로 항목 간격 | 12 | 4 | 24 |
| 세로 행 간격 | 6 | 2 | 16 |
| HUD 높이 | 56 | 44 | 80 |
| 아이콘 크기 | 20 | 12 | 32 |

상단 HUD·필드·하단 HUD 사이의 큰 구역 간격은 0으로 고정한다. 따라서 필드 너비는 `화면 너비 - 가로 외부 패딩×2`, 필드 높이는 `화면 높이 - 세로 외부 패딩×2 - HUD 높이×2`로 계산한다. 가로 항목 간격은 HUD 내부 항목에만, 세로 행 간격은 결과 오버레이의 문장 사이에만 사용하므로 필드 크기를 깎지 않는다.

패널 패딩은 HUD와 결과 패널의 내용 여백에, 아이콘 크기는 임시 사각 아이콘에, HUD 높이는 상·하단 각 구역에 실제로 반영한다. 자동 테스트는 일곱 값을 하나씩 바꿔 해당 화면 치수만 바뀌는지 확인한다.

960x540부터 1920x1080까지의 16:9 크기를 검증하며, 필드는 최소 640x300을 유지한다. 모든 설정을 최댓값으로 올린 960x540에서도 필드는 864x316이므로 기준을 통과한다. 또한 `HUD 높이 ≥ 아이콘 크기 + 패널 패딩×2` 규칙을 검증한다.

## 5. 구현 구조

- `SessionController`: 순수 GDScript 정수 틱·완료 소유자
- `SessionSnapshot`: 화면이 읽는 남은 시간 스냅샷
- `SessionResult`: 정기 종료 사유와 최종 틱 기록
- `UILayoutProfile`: Inspector 조절값
- `UILayoutValidator`: 개별 범위와 최소 필드 검증
- `SessionShell`: HUD·필드·결과 화면과 필드 좌표 변환
- `PrototypeApp`: 기존 밸런스·RNG 구성을 유지하면서 위 객체를 구체적으로 조립

`SessionSnapshot`과 `SessionResult`은 값을 getter로만 노출한다. 화면은 이를 바꿀 수 없고, 과거 스냅샷을 보관하거나 건드려도 컨트롤러의 현재 틱 상태에는 영향을 주지 않는다.

프로토타입에는 인터페이스 계층이나 추상 기반 클래스를 추가하지 않는다. 본 개발의 추상화 범위는 프로토타입 검증이 끝난 뒤 별도로 결정한다.

## 6. 작업 순서

### 작업 1: 빈 세션 시계

명시적인 틱으로만 전진하고 정기 종료 결과를 한 번만 만드는 순수 도메인 코드를 테스트 우선으로 작성한다.

### 작업 2: UI 레이아웃 프로필

확정된 기본값·최솟값·최댓값과 최소 필드 크기를 검증하는 Resource와 Validator를 만든다.

### 작업 3: 세션 셸 화면

Control·Container 기반 상·하단 HUD, 필드, 결과 오버레이, 좌표 변환을 만들고 실제 정렬 결과를 헤드리스 씬 테스트로 확인한다.

### 작업 4: 자동 시작과 결과 전환

`PrototypeApp`이 부팅 시 빈 세션을 시작하고, 물리 틱마다 한 틱을 전진하며, 종료 결과를 한 번만 화면에 반영하도록 연결한다.

유효하지 않은 UI 레이아웃은 물리 처리를 시작하기 전에 필드명이 포함된 오류와 종료 코드 2로 중단되는지도 별도 테스트 씬에서 확인한다.

### 작업 5: 마일스톤 게이트

전체 자동 테스트, 실제 메인 씬 부팅, 2초 테스트 씬, Windows 크기별 수동 확인, Git 위생과 UID 짝을 검증한다.

## 7. 완료 기준

- 기존 Foundation 테스트와 신규 테스트를 합친 6개 스위트 통과
- 실제 Control 배치와 좌표 변환 통합 테스트 통과
- 기본 메인 씬이 입력 없이 180초 세션을 자동 시작
- 2초 테스트 씬이 정기 종료 결과로 정확히 한 번 전환
- 추가 틱을 보내도 두 번째 결과나 전환이 발생하지 않음
- 960x540, 1280x720, 1600x900, 1920x1080에서 HUD 겹침·잘림 없음
- UI 설정 최솟값과 최댓값에서도 최소 640x300 필드 유지
- 일곱 UI 조절값이 각각 지정된 실제 화면 요소에 반영됨
- 잘못된 UI 설정은 세션 틱이 시작되기 전에 안전하게 중단
- 기본 밸런스 180초·60틱 유지
- 시작·재시작·다음·디버그 종료 버튼 없음
- 정산·계약·현금 등 후속 기능이 섞이지 않음
- 신규 GDScript와 UID 파일이 일대일 대응
- 전체 검토 뒤 `Prototyping`에 스쿼시 병합하고 `prototype-m2` 태그 생성

## 8. 브랜치와 현재 미커밋 상태

상세 계획 문서는 `main`에서 관리한다. 새 개발 세션은 `Prototyping`에서 피처 워크트리를 만든 뒤 이 계획 문서 커밋만 피처 브랜치에 가져온다.

최종 병합 전에 기본 `Prototyping` 작업공간의 기존 들여쓰기 변경이 여전히 남아 있으면 작업을 중단하고 사용자에게 정리를 요청한다. 피처 구현이 기존 변경을 임의로 되돌리거나 흡수해서는 안 된다.

검증된 피처는 곧바로 `Prototyping`을 움직이지 않는다. 별도의 깨끗한 후보 워크트리에서 먼저 스쿼시 후보 커밋을 만들고 자동·수동 검증을 다시 통과한 뒤에만 `Prototyping`을 fast-forward한다. 통합 상태를 한 번 더 검증하고 사용자가 증거를 승인한 뒤 `prototype-m2` 태그를 만든다.

`proto/01-session-shell`이 검증된 뒤에만 다음 브랜치인 `proto/02-track-train`의 상세 계획을 작성한다.
